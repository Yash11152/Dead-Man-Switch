## 1. What is `key_material`?

`key_material` is **the raw, plaintext 32-byte (64-character hex) random token** generated by `generateRecipientClaimToken()` in `src/lib/crypto.ts`. It is **not** a passphrase chosen by the user, **not** a derived key, and **not** an encrypted value — it is a cryptographically random secret.

It serves as the **single input secret** from which the recipient's Key Encryption Key (KEK) is derived via PBKDF2. The KEK is then used to unwrap the per-file Data Encryption Keys (DEKs), which in turn decrypt the AES-256-GCM encrypted payload files.

In terms of the key hierarchy:

```
key_material  (64-hex random secret, 256 bits of entropy)
      │
      ▼  PBKDF2-SHA256, 100,000 iterations, salt = "recipient-claim-salt"
recipient KEK  (AES-256-GCM key, non-extractable in WebCrypto)
      │
      ▼  AES-KW (key unwrap)  — applied to encrypted_dek_recipient per file
per-file DEK  (AES-256-GCM key, 256-bit)
      │
      ▼  AES-256-GCM decrypt — applied to ciphertext blob in Storage
plaintext file
```

**The `key_material` is effectively the master unlock password for all files in a switch.** Anyone who obtains it can derive the KEK, unwrap every file's DEK, and decrypt every encrypted payload — without needing the token hash, the signed URL, or even the email verification step.

## 2. Where and How is it Generated?

### Generation Site
**File:** [`src/lib/crypto.ts`](file:///c:/Users/ASUS/Desktop/DEAD%20MAN%20BRO/src/lib/crypto.ts#L187-L195) — lines 187–195

```typescript
export function generateRecipientClaimToken(): {
  rawToken: string;
  tokenHashPromise: Promise<string>;
} {
  const randomBytes = crypto.getRandomValues(new Uint8Array(32));  // 256 bits CSPRNG
  const rawToken = bufferToHex(randomBytes);                        // 64-char hex string
  const tokenHashPromise = computeSHA256(new TextEncoder().encode(rawToken)); // SHA-256 of rawToken
  return { rawToken, tokenHashPromise };
}
```

- Uses `crypto.getRandomValues()` — the browser's CSPRNG. **This is correct and strong.**
- Returns two values: `rawToken` (the secret) and `tokenHashPromise` (SHA-256 of the secret).
- Only the hash (`token_hash`) is used for database lookups.

## 3. Complete Lifecycle Flow

```
SWITCH CREATION
─────────────────────────────────────────────────────────────────────
1. Browser: generateRecipientClaimToken() → rawToken (64-hex)
2. Browser: SHA-256(rawToken) → tokenHash
3. Browser: deriveKEK(rawToken, 'recipient-claim-salt') → recipientKEK
4. Browser: wrapDEK(perFileDEK, recipientKEK) → encrypted_dek_recipient (per file)
5. Browser → Supabase DB: INSERT INTO recipient_claim_tokens
      { token_hash: tokenHash, key_material: rawToken, ... }
   ↑ rawToken is transmitted over HTTPS to Supabase PostgREST endpoint
   ↑ rawToken is stored as plaintext text column in PostgreSQL

SWITCH DETAIL PAGE LOAD (owner dashboard)
─────────────────────────────────────────────────────────────────────
6. Browser → Supabase DB: SELECT id, key_material, expires_at
      FROM recipient_claim_tokens
      WHERE switch_id = ? AND revoked_at IS NULL LIMIT 1
   ↑ rawToken returned from DB → stored in React state: setSwitchKeyMaterial(rawToken)
   ↑ rawToken lives in browser memory for the duration of the page session

TOKEN ROTATION (owner action)
─────────────────────────────────────────────────────────────────────
7. Browser: generateRecipientClaimToken() → newRawToken
8. Browser: re-wraps all file DEKs with deriveKEK(newRawToken, ...)
9. Browser → Supabase: RPC rotate_claim_token({ p_key_material: newRawToken })
   ↑ newRawToken transmitted over HTTPS
   ↑ Stored in DB: INSERT INTO recipient_claim_tokens { key_material: newRawToken }

SWITCH TRIGGER (pg_cron, every minute)
─────────────────────────────────────────────────────────────────────
10. process_switch_expirations() transitions switch to TRIGGERED
    - Looks up existing token (if any) by switch_id + recipient_id + revoked_at IS NULL
    - If none: generates a new token_hash via sha256(gen_random_bytes(32))
      BUT: does NOT set key_material for server-generated tokens
    - Inserts SWITCH_TRIGGERED notification with /claim?grant=<token_id> link

RECIPIENT CLAIM
─────────────────────────────────────────────────────────────────────
11. Recipient opens /claim?grant=<UUID>
12. Recipient types authorized email
13. Browser → POST /api/claim { grant: UUID, email }
14. /api/claim → Supabase RPC redeem_recipient_claim(p_grant_id=UUID, p_recipient_email)
15. RPC validates: not revoked, not expired, redemption limit, switch=TRIGGERED, email match
16. RPC returns: { success: true, key_material: rawToken, files: [...] }
                                   ↑ rawToken travels from DB → PostgREST → Next.js
17. /api/claim returns to browser:
    { keyMaterial: rawToken, files: [...signed URLs...] }
                   ↑ rawToken travels over HTTPS to recipient's browser
18. Browser: deriveKEK(keyMaterial, 'recipient-claim-salt') → recipientKEK
19. Browser: unwrapDEK(encrypted_dek_recipient, recipientKEK) → DEK per file
20. Browser: decryptFile(ciphertextBuffer, iv, DEK) → plaintext blob
21. Browser: triggers download via object URL
```

## 6. Decryption Workflow — How the Recipient Uses It

The recipient decryption flow, end-to-end:

```
Step 1: Recipient receives email with /claim?grant=<token-UUID>
Step 2: Recipient opens claim page, enters their email address
Step 3: Browser POSTs to /api/claim:
          { grant: "uuid-of-token-row", email: "recipient@example.com" }

Step 4: /api/claim calls redeem_recipient_claim(p_grant_id, p_recipient_email)
        RPC checks:
          a. Token exists and is not revoked
          b. Token is not expired  
          c. Redemption count < max_redemptions (default 10)
          d. Switch status = TRIGGERED
          e. Email matches recipient_email (case-insensitive)
        RPC increments redemption_count
        RPC returns: { key_material: rawToken, files: [...] }

Step 5: /api/claim generates 60-second signed URLs for each file
        Returns to browser: { keyMaterial: rawToken, files: [{downloadUrl, ...}] }

Step 6: Recipient clicks "Decrypt & Save" on a file
        Browser fetches ciphertext from signed URL (60s window)

Step 7: Browser calls:
          recipientKek = await deriveKEK(keyMaterial, 'recipient-claim-salt')
          // PBKDF2: 100k iterations, SHA-256

Step 8: Browser parses encrypted_dek_recipient (base64 JSON envelope)
        Browser calls: dek = await unwrapDEK(wrappedKey, iv, recipientKek)
        // AES-GCM decrypt of the wrapped DEK

Step 9: Browser calls: plainBlob = await decryptFile(ciphertext, iv, dek, mimeType)
        // AES-256-GCM decrypt

Step 10: Browser triggers download of decrypted plaintext file
```

**The critical observation:** `key_material` is not needed for Steps 1–5. It is only needed locally in the browser for Steps 7–9. Its value must be transmitted *from the server to the browser* because it was stored server-side. This is the root design constraint that creates the vulnerability.

## 7. Threat Analysis — Compromise Scenarios

### Scenario A: Database Compromised

**Attack:** Attacker gains read access to the `recipient_claim_tokens` table (SQL injection, leaked DB credentials, DB backup exfiltration, Supabase admin console access).

**Impact:** **CATASTROPHIC.** Attacker obtains `key_material` for every switch, every recipient. Can derive all recipient KEKs. Can then download ciphertext blobs from Storage (requires separate Storage access) and decrypt all files. No email verification, no token redemption required — the attacker has the root key.

**Current mitigation:** RLS restricts SELECT to switch owners. But RLS does not protect against: service-role key access, DB superuser access, WAL/backup exfiltration, or Supabase administrative access.

---

### Scenario B: Recipient Email Account Compromised

**Attack:** Attacker gains access to the recipient's email inbox. Finds the `/claim?grant=<UUID>` link in the triggered switch notification email.

**Impact:** **Full file decryption.** The attacker can open the claim link, enter the recipient's email (they have access to it), pass the email verification, and receive `key_material` in the API response. All files are decryptable.

**Note:** This is intended behavior — the email link is the delivery mechanism. But the security analysis shows there is a single factor (email possession + knowledge of email address) protecting all encrypted files. There is no second factor.

---

### Scenario C: Recipient's Browser Session / Device Compromised

**Attack:** Malware, XSS, or browser extension with page access reads `claimedSwitch.keyMaterial` from React state after a successful claim.

**Impact:** **Full file decryption, indefinitely.** Once extracted, `key_material` can be used offline to derive the KEK and decrypt files from any copy of the ciphertext — the 60-second signed URLs only protect fresh downloads, not files already cached. The extracted `key_material` remains valid until the token is rotated or revoked.

---

### Scenario D: Owner Dashboard XSS or Session Compromise

**Attack:** XSS on the dashboard reads `switchKeyMaterial` from React state.

**Impact:** **Full file decryption, indefinitely.** Same as Scenario C. The owner's dashboard loads `key_material` on every page visit even when the switch is ACTIVE (before triggering), so the attacker gains the recipient's decryption key even if the switch has never been triggered.

---

### Scenario E: HTTPS/TLS Intercepted (e.g., corporate proxy, compromised CA)

**Attack:** Network-level interception of the HTTPS response from `/api/claim`.

**Impact:** `keyMaterial` field visible in plaintext in the response JSON body. Complete file decryption possible.

**Current mitigation:** HSTS, certificate pinning (not implemented). Standard web HTTPS protects against opportunistic interception but not against targeted enterprise proxy or CA-level attacks.

---

### Scenario F: Claim Token (UUID) Stolen, Email Not Known

**Attack:** Attacker intercepts the `/claim?grant=<UUID>` link URL (from email forwarding, URL shortener log, referrer header, server log) but does not have the recipient email address.

**Impact:** **Blocked by email verification in `redeem_recipient_claim`.** The RPC checks that `LOWER(TRIM(v_recipient.recipient_email)) = LOWER(TRIM(p_recipient_email))`. Attacker cannot proceed without knowing the authorized email.

**Note:** This is the **only** protection against token theft that does not require `key_material` being known. If email is guessable (e.g., attacker already knows who the recipient is), this check provides minimal protection.

---

### Scenario G: Supabase PostgREST / CDN Request Logging

**Attack:** Supabase enables PostgREST query logging or response body logging. Admin views logs.

**Impact:** `key_material` returned by `redeem_recipient_claim` and transmitted to `/api/claim` may appear in RPC response logs. Supabase does not log RPC response bodies by default, but this depends on Supabase configuration and logging level.

## 8. Proposed Safer Designs

---

### Design A: ECDH Key Agreement — Recipient Key Never Leaves Their Browser

**Core Idea:** Instead of storing a symmetric secret in the database, the system uses an asymmetric key pair. The recipient's public key is stored server-side. When the owner wraps file DEKs, they encrypt them to the recipient's public key (ECDH/ECIES). The recipient's private key never touches the server or the database.

#### How It Works

**During switch creation:**
1. The recipient's browser generates an ephemeral ECDH key pair client-side.  
   *(Requires recipient to be on the platform OR the owner sets up a passphrase for the recipient — see below.)*
2. The public key is stored in the database (not secret — public keys can be stored openly).
3. The private key is delivered to the recipient out-of-band (encrypted to their passphrase, or emailed as a one-time download link).
4. File DEKs are encrypted using the recipient's public key (ECIES / ECDH + AES-KW).

**During claim:**
1. Recipient provides their private key (or passphrase to derive it).
2. `key_material` column is **not needed and can be dropped entirely**.
3. All validation (token, email, switch status) works identically.
4. The database never stores the secret.

#### Practical variant (passphrase-derived key pair):
Since the recipient is an external party who may not have a pre-established key pair, a **deterministic ECDH key pair derived from a passphrase** can be used:

- Owner and recipient share a passphrase out-of-band (e.g., verbally, by post).
- Owner's browser: `passphrase → PBKDF2 → ECDH private key → ECDH public key`
- DEKs wrapped to the ECDH public key.
- DB stores only the public key (non-secret).
- On claim: recipient types passphrase → browser derives same ECDH key pair → unwraps DEKs.
- `key_material` column stores the ECDH **public key** (not secret), or is eliminated entirely.

#### Security analysis:
- **Database compromise:** Exposes only public key. Attacker cannot decrypt files without the private key / passphrase, which is never stored.
- **Email compromise:** Attacker gets the claim link (UUID) but not the private key/passphrase. Files remain encrypted.
- **Browser session compromise:** Private key is derived on demand from passphrase — if passphrase is not cached, attacker cannot derive it retroactively.
- **Limitation:** Requires a secure out-of-band channel to deliver the passphrase to the recipient. If the passphrase is emailed, security degrades to current email-compromise scenario.

---

### Design B: Split-Knowledge — Encrypt `key_material` with a Server-Side Application Secret

**Core Idea:** Keep the existing symmetric flow but stop storing `key_material` in plaintext. Encrypt it with a server-side secret (Application Encryption Key, AEK) that lives only in environment variables — never in the database.

#### How It Works

**New environment variable:**
```
APP_ENCRYPTION_KEY=<32-byte-hex AES-256 key, server-only, never committed>
```

**During switch creation (browser → server):**
1. Browser generates `rawToken` as today.
2. Instead of calling `supabase.from('recipient_claim_tokens').insert({ key_material: rawToken })` directly from the browser, the browser POSTs to a **new server-side API route** (e.g., `/api/switch/create`).
3. The server route:
   - Receives `rawToken` in request body (over HTTPS).
   - Encrypts it: `encryptedKeyMaterial = AES-256-GCM(rawToken, AEK, randomIV)`
   - Stores only `encryptedKeyMaterial` and `iv` in the DB column (renames `key_material` to `encrypted_key_material`).
4. `rawToken` is **never stored in plaintext** anywhere.

**During owner dashboard load:**
- The dashboard does **not** fetch `encrypted_key_material` from the DB at all.
- Instead, when a new file is uploaded, the browser sends the raw token to a server route that re-derives the recipient KEK server-side.
- **Or:** The DB stores `encrypted_dek_recipient` only. The owner can re-wrap at upload time by fetching the encrypted key material, decrypting it server-side, and returning it only for the specific re-keying operation.

**During claim:**
1. `redeem_recipient_claim` RPC returns `encrypted_key_material` (the AES-encrypted blob).
2. `/api/claim` route **decrypts** it server-side: `rawToken = AES-GCM.decrypt(encrypted_key_material, AEK)`.
3. Returns `keyMaterial: rawToken` to browser as today (or avoids returning it — see below).

#### Further hardening (avoid sending `key_material` to browser at all):
Instead of returning `keyMaterial` to the browser, perform DEK unwrapping server-side:

1. `/api/claim` decrypts `encrypted_key_material` → `rawToken` (server-side only).
2. For each file, server-side:
   - Derives `recipientKEK = PBKDF2(rawToken, 'recipient-claim-salt')` using Node.js crypto.
   - Unwraps DEK: `dek = AES-GCM-decrypt(encrypted_dek_recipient, recipientKEK)`.
   - Decrypts file: downloads from Storage, `plaintext = AES-GCM-decrypt(ciphertext, dek)`.
   - Streams or returns plaintext directly (or issues a signed URL to a server-decrypted copy).
3. Browser **never receives `rawToken`**.

This eliminates `keyMaterial` from the HTTP response entirely.

#### Security analysis:
- **Database compromise:** Attacker obtains `encrypted_key_material`. Without `APP_ENCRYPTION_KEY`, they cannot decrypt it. Files remain secure.
- **Email compromise:** Same as today — attacker can claim the token. But `rawToken` is only held in server memory briefly, not in browser memory or DB plaintext.
- **Browser session XSS:** `keyMaterial` can be removed from the browser response entirely (server-side decryption variant), eliminating this attack surface.
- **Server compromise:** If `APP_ENCRYPTION_KEY` and the DB are both compromised simultaneously, security degrades to today's level. This is the residual threat model.
- **Limitation:** Requires a server-side Next.js route for switch creation and rotation (instead of direct Supabase SDK calls from the browser). Moderate implementation complexity.

## 9. Design Comparison

| Criterion | Current Design | Design A: ECDH Key Agreement | Design B: Server-Side Encryption of `key_material` |
|---|---|---|---|
| **`key_material` in DB** | Plaintext | Not stored (public key only, non-secret) | Encrypted (AES-256-GCM with app secret) |
| **`key_material` in HTTP response** | Yes (JSON body of `/api/claim`) | Not applicable | Optional — can be eliminated entirely |
| **`key_material` in browser memory** | Yes (React state, dashboard + claim pages) | Never — only recipient's private key (derived) | Optional — can be eliminated |
| **DB compromise impact** | All files decryptable | No impact on file security | Files secure (need AEK too) |
| **Email account compromise** | Full decryption | Partial (need passphrase too) | Full decryption (unchanged) |
| **Second factor required** | No | Yes (passphrase or private key) | No |
| **Implementation complexity** | Baseline | High — requires cryptographic redesign, out-of-band passphrase delivery | Medium — server routes + env variable + migration |
| **Migration effort** | Baseline | High — all existing files must be re-encrypted to new scheme | Medium — existing files need DEK re-wrapping; `key_material` column encrypted in-place |
| **Recipient UX impact** | None (email link only) | Moderate — recipient must remember/enter a passphrase | Minimal — same UX as today |
| **Security vs. current** | Baseline | Significantly stronger | Meaningfully stronger |
| **Existing encryption broken?** | No | No — DEK wrapping changes, AES-256-GCM for files unchanged | No — only `key_material` storage layer changes |
| **Backward compatibility** | Baseline | Requires re-keying all existing switches | Requires one-time migration to encrypt existing `key_material` rows |

## 10. Summary of Findings

### Q1: What exactly is `key_material`?

A cryptographically random 32-byte (256-bit) secret generated client-side using `crypto.getRandomValues()`. It is the **sole input secret** to PBKDF2 that produces the recipient's Key Encryption Key (KEK). It is effectively the **master unlock password** for all payload files in a switch. It is not a passphrase chosen by a user, not derived from any user secret, and not an already-encrypted value.

**Files:** [`src/lib/crypto.ts:187–195`](file:///c:/Users/ASUS/Desktop/DEAD%20MAN%20BRO/src/lib/crypto.ts#L187-L195)

### Q5: How does the recipient use it to decrypt files?

`key_material` is passed to `deriveKEK(keyMaterial, 'recipient-claim-salt')` using PBKDF2 (100k iterations, SHA-256) to produce a 256-bit AES-GCM key. This KEK is used in `unwrapDEK()` to decrypt each file's `encrypted_dek_recipient`, yielding the per-file DEK. The DEK is then used in `decryptFile()` to AES-256-GCM decrypt the ciphertext blob fetched via a 60-second signed Storage URL. All decryption occurs client-side in the browser's WebCrypto API.

### Q6: What happens if each party is compromised?

| Compromised Party | Impact |
|---|---|
| **Database** | All `key_material` values exposed → all encrypted files decryptable with Storage access |
| **Recipient email account** | Attacker claims token, passes email check, receives `key_material`, decrypts all files |
| **Claim token (UUID stolen)** | Blocked by email verification — cannot proceed without recipient's email |
| **Browser session (XSS/malware)** | `key_material` readable from React state → all files decryptable indefinitely |
| **Owner dashboard session** | `switchKeyMaterial` React state leaks `key_material` even before switch triggers |

### Top Recommended Fix Priority

1. **Immediate (P1):** Implement **Design B** (server-side encryption of `key_material`) — eliminates plaintext DB storage and optionally removes `key_material` from HTTP responses. Moderate implementation effort. Does not break the recipient UX.

2. **Medium-term (P2):** Extend toward **Design A** (ECDH/passphrase-derived keys) for new switches — eliminates the need for any server-stored secret, adds a second factor (passphrase) protecting against email compromise scenarios.

3. **Near-term (P3):** Even before a full redesign, remove `keyMaterial` from the `/api/claim` JSON response and perform DEK unwrapping + file decryption server-side (Node.js crypto) to avoid exposing the raw secret to the browser entirely.
